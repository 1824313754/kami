# 2FA 重新授权与重试

账号正常授权顺序是提交邮箱、提交密码、根据已导入密钥生成并提交动态验证码、取得并刷新令牌，最后回写原账号。

MFA 同时支持上游返回 `page.payload.factor_id`、`page.payload.factors`、响应中的 `oai-client-auth-session.mfa_factors` 和原有会话补查。直接返回的 `factor_id` 优先使用，其他格式保留原行为。

## 默认重试规则

- 每个账号最多尝试 3 次，包含首次请求，即最多追加 2 次完整授权。
- 每次调用重新创建授权流程；成功并取得完整令牌后停止重试，再回写账号。全部失败只计该账号失败一次。
- 关键过程日志显示尝试次数，以及失败后的重试提示；异常内容继续使用现有公开错误分类，不输出密码、密钥或令牌。
- 沿用现有异常分类：已识别的账户封禁、`rate_limit_exceeded` 不立即重试。限流仍按现有 5 分钟冷却处理。
- 每次尝试开始前检查任务停止状态。已发出的网络请求仍需结束或超时，停止任务会阻止下一次尝试。
- 部分底层 HTTP 请求另有自身重试，所以实际网络请求数可能超过 3；这里的 3 次指完整账号授权尝试。

## Docker 更新与故障定位

发布到 GHCR 后，生产目录使用指向 `ghcr.io/1824313754/kami:main` 的 Compose 配置，执行 `docker compose pull` 和 `docker compose up -d --no-build --remove-orphans` 更新；数据目录保持原挂载。首次切换参见 [部署文档](docker-deploy.md)。

“OAuth 流程执行失败，请查看关键过程日志”是未匹配已知错误类型时的统一提示，并不能说明失败发生在 2FA。缺少验证方式的异常包含 `2FA`，按现有分类应显示 2FA 验证失败，而不是这条通用文案。

此次生产实例日志未提供，本地找到的同文案记录属于旧邮箱授权任务。当前账号任务捕获未知异常时只记录公开文案，未保存该异常的原始堆栈，因此历史通用提示可能不足以还原根因。可在生产目录执行 `docker compose logs --since 30m --no-color pyfaka`，结合失败时间、任务编号和账号关键过程日志定位；日志若同样缺少底层错误，需要另补诊断信息。重试改善偶发失败，不代表已经修复该次生产故障的原因。
